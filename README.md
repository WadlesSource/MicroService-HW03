## Домашнее задание к занятию «Микросервисы: подходы»
# Задача 1: Обеспечить разработку  
Для организации процессов разработки, непрерывной интеграции и поставки (CI/CD) в микросервисной архитектуре оптимальным решением станет GitLab SaaS (облачная версия GitLab.com) в связке с гибридными GitLab Runners и внешним менеджером секретов (HashiCorp Vault).  
Это единая DevSecOps-платформа, которая исключает необходимость настраивать сложные интеграции между разрозненными системами для кода, сборок и артефактов, закрывая все поставленные требования.  
### Соответствие требованиям бизнеса  
Ниже приведено обоснование того, как предложенный стек закрывает каждый пункт технического задания:  
| Требование | Реализация в предложенном решении | 
| ------------- | ------------- | 
| Облачная система и Git | Используется облачный GitLab.com, построенный на базе системы контроля версий Git с высоким уровнем доступности (SLA) |  
| Репозиторий на каждый сервис | Иерархия Groups / Subgroups позволяет удобно структурировать сотни отдельных репозиториев и управлять общими настройками на уровне всей компании |  
| Запуск по событию из VCS | Встроенные триггеры автоматически запускают пайплайны при push, создании Merge Request, добавлении тегов или по расписанию (Cron) |  
| Запуск по кнопке с параметрами | Директива when: manual в файле конфигурации .gitlab-ci.yml позволяет запускать этапы вручную через веб-интерфейс, передавая кастомные переменные (variables) |  
| Привязка настроек к сборке	| Конфигурация хранится как код (Pipeline as Code) в файле .gitlab-ci.yml внутри репозитория, что жестко привязывает настройки сборки к конкретному коммиту и ветке |  
| Шаблоны конфигураций | Механизм include позволяет вынести базовые сценарии сборок в отдельный центральный репозиторий шаблонов и подключать их в микросервисы в пару строк | 
| Безопасное хранение секретов | Нативная связка GitLab + HashiCorp Vault (или использование маскируемых защищенных переменных GitLab CI/CD Variables для базовых нужд) исключает утечку ключей |  
| Несколько конфигураций из 1 репо | Поддерживается через Parent-Child Pipelines (дочерние пайплайны) и правила rules, которые запускают разные сценарии в зависимости от измененных файлов или ветки |  
| Кастомные шаги и Docker-образы | Каждый шаг (job) описывается произвольными shell-скриптами и может выполняться внутри любого указанного в теге image: собственного Docker-образа из реестра |  
| Свои агенты сборки | GitLab Runner легко устанавливается на собственные Linux/Windows-серверы или разворачивается в корпоративном Kubernetes с автоскалированием подов под нагрузку |  
| Параллельные сборки и тесты | Независимые джобы внутри одного этапа (stage) запускаются одновременно. Для ускорения тестов используется ключевое слово parallel, которое автоматически дробит набор тестов на                                                 несколько параллельных потоков |  
# Задача 2: Логи  
Для организации централизованного сбора, хранения и анализа логов в микросервисной архитектуре оптимальным решением станет стек на базе Vector, Apache Kafka (опционально для сверхвысоких нагрузок) и OpenSearch (в связке с OpenSearch Dashboards).  
Такая архитектура обеспечивает высокую отказоустойчивость, не нагружает сами микросервисы и предоставляет разработчикам мощный и привычный инструмент для поиска и отладки.  
### Соответствие требованиям бизнеса  
Ниже приведено обоснование того, как предложенный стек закрывает каждый пункт технического задания:  
| Требование | Реализация в предложенном решении |
| ------------- | ------------- | 
| Сбор со всех хостов в единый центр	| Vector разворачивается как системный демон (или DaemonSet в K8s) на каждом сервере, собирая логи всех запущенных сервисов в единый кластер OpenSearch |
| Минимальные требования (сбор из stdout)	| Микросервисы выводят логи исключительно в stdout. Движок контейнеров (containerd/Docker) сам записывает их в системные файлы на хосте, откуда их забирает агент |
| Гарантированная доставка	| Обеспечивается на двух уровнях: сохранение смещения чтения файлов (offset) и локальный дисковый буфер в Vector плюс репликация и хранение сообщений в Kafka до подтверждения записи |
| Поиск и фильтрация	| OpenSearch поддерживает полнотекстовый поиск, фильтрацию по любым JSON-полям (уровень ошибки, trace_id, имя сервиса) и язык запросов DQL/Lucene |
| UI и разграничение прав доступа	| OpenSearch Dashboards имеет встроенный модуль безопасности (Security Plugin) с поддержкой SSO/LDAP и ролевой моделью (RBAC), позволяя выдавать разработчикам доступ только к логам их сервисов |
| Ссылка на сохранённый поиск	| В OpenSearch Dashboards любой поисковый запрос с выбранными фильтрами и временным интервалом можно сохранить как объект (Saved Search) или сгенерировать короткую прямую ссылку (Permalink) для отправки в чат |  
# Задача 3: Мониторинг  
Для организации централизованного мониторинга инфраструктуры и приложений в микросервисной архитектуре отраслевым стандартом и оптимальным решением является стек на базе Prometheus (в связке с VictoriaMetrics для долгосрочного хранения), набора экспортеров (Node Exporter, cAdvisor) и Grafana.  
Данная архитектура построена на pull-модели сбора данных, отлично масштабируется под динамическую среду микросервисов и предоставляет мощные инструменты аналитики и визуализации.  
### Соответствие требованиям бизнеса  
Ниже приведено обоснование того, как предложенный стек закрывает каждый пункт технического задания:  
| Требование	| Реализация в предложенном решении |
| ------------- | ------------- | 
| Сбор со всех хостов системы	| Механизм Service Discovery автоматически находит все серверы и поды в кластере, обеспечивая непрерывный сбор данных без ручного редактирования конфигов |
| Метрики ресурсов хостов (CPU, RAM, HDD, Net)	| Node Exporter собирает исчерпывающую телеметрию ядра Linux: загрузку процессоров, свободную/занятую память, IOPS и место на дисках, сетевой трафик и ошибки пакетов |
| Метрики ресурсов каждого сервиса	| cAdvisor (и встроенные метрики Kubernetes kube-state-metrics) отслеживает потребление CPU, RAM, дискового I/O и сети в разрезе каждого отдельного контейнера и микросервиса |
| Специфичные метрики сервисов	| Разработчики добавляют кастомные счетчики (RPS, время ответа, ошибки, бизнес-метрики) через Prometheus Client Libraries, а Prometheus забирает их с эндпоинта /metrics |
| UI для запросов и агрегации	| Встроенный в Grafana режим Explore позволяет писать сложные аналитические запросы на языке PromQL / MetricsQL (расчет перцентилей, скорости роста, средних значений) |
| UI для настройки панелей (дашбордов)	| Grafana позволяет создавать интерактивные дашборды с графиками, таблицами и индикаторами, а также импортировать тысячи готовых шаблонов от сообщества |
